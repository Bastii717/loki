# Contributing to Loki

Thanks for your interest. Loki is a small project with a single maintainer, so this document is short and practical: what to do before you write code, how the repository is laid out, which conventions keep it consistent, and how a change becomes a release.

## Before you write code

- **Talk first for anything bigger than a bug fix.** Open a [feature request](https://github.com/Bastii717/loki/issues/new?template=feature_request.yml) and describe the problem, not only the solution. Loki has a clear scope (a private, team-internal board behind single sign-on, nothing public), and a short discussion avoids work that cannot be merged.
- **Bugs** go through the [bug report](https://github.com/Bastii717/loki/issues/new?template=bug_report.yml) template; a pull request with a failing test is even better.
- **Security problems** are reported privately, see [SECURITY.md](SECURITY.md).

## Repository layout

| Path                   | What lives there                                                                                                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/routes/`          | SvelteKit pages, form actions and API endpoints. `src/routes/api/` is JSON, everything else renders pages.                                                                        |
| `src/lib/components/`  | Svelte components shared across pages.                                                                                                                                            |
| `src/lib/server/`      | Everything that must never reach the browser: database access (`db/`), auth and sessions (`auth/`), the domain modules (feed, comments, moderation, mail, …) and background jobs. |
| `src/hooks.server.ts`  | The single request guard: sessions, roles, rules acceptance, maintenance write lock, rate limiting, security headers. Authorisation lives here, not in individual pages.          |
| `src/lib/changelog.ts` | The "What's new" entries members see after an update.                                                                                                                             |
| `drizzle/`             | SQL migrations and their snapshots, generated by Drizzle Kit and applied at application start.                                                                                    |
| `scripts/`             | Developer tooling: demo seed, README screenshots, contrast check.                                                                                                                 |
| `backup/`              | The backup and restore container with its runbook.                                                                                                                                |
| `docs/`                | `deployment.md` (operators) and the README screenshots.                                                                                                                           |
| `static/`              | Icons, manifest, the static outage page.                                                                                                                                          |
| `.github/`             | CI, image publishing, Dependabot, issue and pull request templates.                                                                                                               |

## Development setup

```sh
cp .env.dev.example .env
docker compose -f docker-compose.dev.yml up -d   # Postgres, MinIO, mock OIDC, Mailpit
npm install
npm run dev
```

The mock identity provider accepts any username; the claims JSON decides the role, for example `{"preferred_username":"dev","groups":["loki-members","loki-admins"]}`. `npx tsx --env-file=.env scripts/seed-demo.ts` creates demo memes, quotes and users. Feedback mails land in Mailpit at `http://localhost:8025`.

Checks that must pass:

```sh
npm test          # Vitest; uses the dev database and truncates it
npm run lint      # Prettier and ESLint
npm run check     # svelte-check / TypeScript
```

Tests run against the real Postgres and MinIO of the dev stack on purpose; most modules have no mocks. Never run two test processes at the same time against one database.

## Conventions

- **English everywhere**: UI copy, code, comments, commit messages, docs.
- **UI copy** is plain and short, sentence case, no emojis. Icons are local SVGs (lucide style) under version control; nothing is loaded from a CDN.
- **Design tokens** come from `src/app.css` (`--surface`, `--accent`, `--radius`, …). New UI uses them so the light theme and the seasonal themes keep working.
- **Authorisation** is enforced in `src/hooks.server.ts` and the server modules, never only in a page or component. A new route that needs a role uses the existing helpers (`requireModerator`, the guard's path lists) instead of a new check.
- **Nothing public**: media is streamed or presigned through the app, ids in links are random public ids, and no feature may expose content without a session.
- **Tests first**: a change comes with tests that exercise real behaviour (database-backed where the code touches the database). Edge cases that matter to a person using the app (empty input, limits, the no-JavaScript path of a form) get a test too.
- **Schema changes** ship as a Drizzle migration: edit `src/lib/server/db/schema.ts`, run `npx drizzle-kit generate --name <what_changed>`, commit the SQL, the snapshot and the journal together.
- **Commits** follow Conventional Commits (`feat(scope): …`, `fix(scope): …`, `docs: …`, `chore: …`); one topic per commit, imperative mood, a body when the why is not obvious.
- **No personal or infrastructure data** in the repository: no hostnames, addresses, real names or internal URLs in code, tests, docs or fixtures. Demo data uses invented names.

## Pull requests

1. Branch from `main` (`feat/…`, `fix/…`, `docs/…`, `chore/…`).
2. Keep the pull request focused; split unrelated changes.
3. Fill in the template: what changes from the user's point of view, and the checklist.
4. CI must be green (lint, type check, tests, secret scan, image build). A pull request builds the image but does not publish it.
5. Update the docs that the change touches in the same pull request: the README feature list, `docs/deployment.md` (environment variables, operations notes), `.env.example` and `.env.dev.example`, `backup/README.md` for the backup job.
6. A user-visible change adds a short, plain-language line to `src/lib/changelog.ts` under the upcoming version.

The maintainer reviews, may ask for changes, and merges with a merge commit.

## Releases (maintainer)

Releases are tags. Pushing `vX.Y.Z` on `main` builds the multi-arch image, publishes it to GHCR as `X.Y.Z`, `X.Y`, `vX` and `latest`, and signs it with cosign. The GitHub release carries the notes for operators and members, grouped as Features / Bug fixes / Operations, where Operations says whether migrations run, which variables are new and what to do after the pull. The same text is kept in [CHANGELOG.md](CHANGELOG.md). Details in `docs/deployment.md` under "Releases".
